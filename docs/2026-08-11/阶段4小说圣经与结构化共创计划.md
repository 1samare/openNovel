# 阶段 4 小说圣经与结构化共创实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 本项目阶段 1–8 固定在根工作区 `feat/v1.0` 实施，不新建 worktree；当前任务未获子 Agent 或 GitHub Actions 授权，全部实现与验证在当前会话、本地命令中完成。

**目标：** 交付可追溯、可恢复的小说圣经与结构化共创闭环，使用户可以维护作品档案、世界设定、人物和分层大纲，并审核设定/人物/剧情 Agent 产生的少量高价值提案。

**架构：** 项目 schema v4 使用分领域实体表保存可查询的当前资料，以统一追加式 `bible_source_versions` 保存每次权威版本，提案在批准前独立暂存。renderer 只使用固定 `novelBible` IPC；主进程 Bible Runtime 组合项目数据库服务和 Model Runtime 的内部结构化角色路由，供应商 SDK 不越出 `src/model/`，Agent 结果未经用户审批不能进入权威资料。

**技术栈：** Electron 43、Vue 3、TypeScript 6、Node 24/26 `node:sqlite` Worker、Vercel AI SDK、Zod、Node Test Runner、Vitest 与现有生产 Electron smoke。

## 全局约束

- 仅实现阶段 4；不实现阶段 5 的正文生成、选区 AI、真实 `ModelExecutor` 或多 Agent 正文 Workflow Controller。
- 世界观区分 `urban-campus` 与 `sci-fi-future` 主类型；主类型首次保存后不可静默切换，但允许用户手工增加另一题材的条目。
- 用户手工保存的资料直接标记 `user_confirmed`；Agent 结果只能以 `proposed` 提案保存，批准后才形成 `approved` 权威版本。
- 资料版本只追加不原地覆盖历史；替代、恢复、批准和拒绝均写入审计，旧版本保留并可追溯。
- 冲突必须显示旧值、新值、来源版本和影响对象；没有明确替代确认时返回冲突，不自动选择新旧资料。
- Proposal/输出 schema 在模型调用和持久化前都严格校验；额外字段拒绝，无效结构只允许一次定向修复。
- 共创上下文只包含 `user_confirmed` 与 `approved` 资料；`proposed`、`rejected`、`superseded` 不作为权威事实约束后续生成。
- 主编精选最多展示 3 条提案，按明确影响、冲突证据和可执行性排序；不为数量而展示低价值建议。
- 页面沿用现有暖纸色、中文编辑工具风格；使用语义 HTML、可见标签/焦点、44px 控件、文本状态提示、键盘排序替代和 820px/520px 响应式降级。
- 不新增运行时依赖，不读取、修改、清理或暂存用户既有 `.superpowers/`；不修改或触发 `.github/workflows/`。
- 修改任何受维护目录时同步其 `README.md`；完成前运行 `npm.cmd run check:readmes`。

## 修改目标、范围与明确不包含内容

### 修改目标

1. 建立作品档案、世界设定、地点、势力、物品、人物、关系、人物状态、总纲、分卷、故事阶段、章节规划、时间线、伏笔、提案与来源版本的 project schema v4。
2. 提供统一且严格的共享契约、固定 IPC、preload 响应守卫和脱敏错误边界。
3. 实现手工资料直写、追加式版本、历史恢复、排序、审计、冲突检测以及提案批准/拒绝/替代状态机。
4. 实现设定、人物、剧情三类 Zod 结构化输出和 Prompt 模板，通过已配置角色/模式路由调用 Model Gateway。
5. 交付世界观、人物和大纲三个真实页面，以及共享的提案审阅、版本恢复和错误/空状态体验。
6. 用两类题材夹具验证从空项目到世界观、主要人物和前三章规划的本地/结构化共创闭环，验证重启一致性与拒绝提案隔离。

### 明确不包含

- 不将阶段四共创直接接入现有离线 AI 对话 Harness；该 Harness 保持历史用途，阶段五再接入真实小说 Workflow Controller。
- 不生成、保存或确认章节正文，不实现 1500–3000 字门禁、语义审校或章节事实提取。
- 不实现 FTS/Embedding/RAG、人物关系图可视化、时间线图、批量章节规划、拖拽专用库或自动从正文反向同步。
- 不允许 renderer 读取数据库、文件路径、API Key、供应商原始响应或通用 IPC/fetch。
- 不自动批准模型提案，不把拒绝提案放入后续 Prompt，不用测试 fake provider 冒充真实供应商验收。

## 设计复核与取舍

1. **采用：分领域当前表 + 统一追加式来源版本账本。** 当前资料可用外键和索引查询，版本、来源和恢复逻辑保持统一，符合总计划逐类建表要求。
2. **未采用：单一 `bible_entities` JSON 大表。** 扩展快，但人物关系、层级大纲和类型约束会退化为运行时约定，迁移与冲突定位较弱。
3. **未采用：完整事件溯源。** 审计能力最强，但读取模型、重放、投影与迁移成本超出 V1；现有追加版本与 `audit_events` 已能满足追溯和恢复。

UI 采用三个专用路由共享 composable/组件，而不是一个巨型通用表单；Model 调用采用主进程内部角色路由，而不是把模型能力暴露给 renderer 或提前改造阶段五 Orchestrator。
